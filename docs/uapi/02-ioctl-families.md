## 2. Device `ioctl`s, by family

Dispatched on the whole request word (magic byte plus command), never on the command byte
alone — the one time that was done wrong, `RNDADDENTROPY` (`'R'` nr 3) was answered as the
drain (`'R'` nr 4) and OpenRC's `seedrng` failed to seed the boot (`docs/notes/` §12.1 A8).

| `'d'` (0x64) | `/dev/dri/card0`, `renderD128` | `src/drivers/drm/`, `crates/gpu/src/virtgpu.rs`, `crates/gpu/src/*.rs` | Served across the compositor surface, and **the `DRM_VIRTGPU_*` family with it, 2D and 3D both**: all eleven requests are dispatched, and each answers per card shape, as Linux's does (measured; the instrument was `user/staging/virtgpu-probe/`, now deleted - its table is in `docs/notes/` §7.4, and the GL card's own answers too). On a card with no 3D — `GETPARAM` (`3D_FEATURES` 0, `CAPSET_QUERY_FIX` 1, unknown parameter `EINVAL`, the write four bytes wide as Linux's is), `RESOURCE_CREATE` (a real device resource, made across the mailbox to the render task), and `RESOURCE_INFO`/`MAP`/`WAIT`/`TRANSFER_TO_HOST` for the handle it returns; `GET_CAPS`/`EXECBUFFER`/`TRANSFER_FROM_HOST` `ENOSYS`, `CONTEXT_INIT`/`RESOURCE_CREATE_BLOB`/a 3D `RESOURCE_CREATE` `EINVAL`. On a GL card the same requests answer as Linux's GL card does: `VIRGL` and `CONTEXT_INIT` are negotiated (`3D_FEATURES` 1, `SUPPORTED_CAPSET_IDs` 6), `CONTEXT_INIT` is `EEXIST` because the context is created implicitly on the first resource, a 3D `RESOURCE_CREATE`, `EXECBUFFER` and `TRANSFER_FROM_HOST` complete, and the two advertised cap sets are fetched and cached. **And the context that names a resource is told about it first**: `EXECBUFFER` resolves its `bo_handles` and attaches their resource ids to the submitting file description's context — the pairs sent are remembered per context, so only the first stream to name a resource pays a control-queue round trip — and each 3D transfer does the same for the one resource it names. That is not decoration: `vrend` resolves a resource *per context* and **drops the whole batch** over an id its context has not been told about, which is what a compositor's own buffer was, because Mesa's GBM buffers arrive as `target == 2` creates and this card's 2D create path attached nothing (`docs/notes/` §7.4). Pinned by `t-virtgpu`'s three claims — the file that *made* the resource, a file that *imported* its descriptor, and the resource that takes over the id a release freed (a resource id here is a handle slot, so the release also tells each context to let go of it, Linux's `gem_object_close`) — and each claim is read out of the resource's own pages rather than out of an errno, because QEMU answers a dropped batch `OK_NODATA`. **And a compositor's frame reaches the display the way Linux's does**: a flip or commit of a framebuffer whose pixels the *device* holds — a client resource made through this family on a card with 3D, `Resource::host_pixels` — is presented by `SET_SCANOUT` + `RESOURCE_FLUSH` of that framebuffer's own resource (`client_scanout`/`Gpu::scan_out_client`), not by copying guest pages that were never written; the kernel's own framebuffer is scanned out again when the compositor lets the screen go, and a framebuffer whose pixels *are* the guest's (a dumb buffer drawn by a software rasteriser, an imported dma-buf) keeps the copy that carries it correctly. Measured: niri's committed 1280x800 framebuffer was 4096000 bytes of zero while it drew into it (`.workbuddy/probe-fb-pixels`), and the same boot now says `virtio-gpu: scanning out the compositor's resource 4` once (`docs/notes/` §7.4). The picture in the window is the step no headless run takes — named open there. **And a client's resources are created the way Linux creates them**: on a card that negotiated 3D every `RESOURCE_CREATE` goes through `RESOURCE_CREATE_3D` whatever its `target` (`three_d = card().virgl`, Linux's `virtio_gpu_object_create` gate), because the 2D command is `resource_id`/`format`/`width`/`height` and has nowhere to put the `bind`, `array_size`, `last_level`, `nr_samples` or `flags` a virgl client asks for — and the host's GL says so (`GL_INVALID_OPERATION`, 1282) when a resource it was given that way is later bound as the render target, depth attachment or vertex buffer its caller meant. `RESOURCE_CREATE_BLOB` stays `EINVAL` on both shapes, which is Linux's answer on both too. **One named divergence left, of three**: `RESOURCE_INFO`'s `res_handle` **was** 0 for a plain dumb buffer and `TRANSFER_TO_HOST` on one **was** `EINVAL`, where Linux names a resource and completes the copy - both closed by making the resource on the first request that addresses the handle as one (`drivers/drm/`'s `back_dumb_with_a_resource`; Linux makes it at `CREATE_DUMB`, and this card makes it later because the console, weston and the fbdev node all allocate dumb buffers and none of them ever asks). The one left is a *refusal*: a transfer whose rectangle does not fit the backing the device was given is refused where Linux would read past it. Both closed halves are pinned by `t-drm` - a dumb buffer's `RESOURCE_INFO` is non-zero and idempotent, its `TRANSFER_TO_HOST` completes, and a handle the card never made is still `ENOENT`. A framebuffer belongs to the open file description that made it and is released with it (Linux's `drm_file_free` → `drm_fb_release`), so `GETRESOURCES`'s `count_fbs` is a list of **that description's** live framebuffers — another description's is not in it, because Linux walks `file_priv->fbs` while the crtc/connector/encoder lists are the card's — and an fb has no property list at all: `OBJ_GETPROPERTIES` on one is `EINVAL`, as Linux's is, since `width`/`height`/`format`/`modifier` are `struct drm_framebuffer` fields and `GETFB2` reports them (`docs/uapi/` §5.1 item 68). The cursor plane publishes `SRC_X`/`SRC_Y`/`SRC_W`/`SRC_H` and `CRTC_W`/`CRTC_H` beside `type`/`FB_ID`/`CRTC_ID`/`CRTC_X`/`CRTC_Y`/`IN_FORMATS`, because a compositor adds them to every plane's atomic state and one the plane does not have reaches the card as property 0 and refuses the whole commit; this cursor cannot scale or crop, so the identity rectangle is the only one a commit may name and any other is `EINVAL`. `DRM_CLIENT_CAP_ATOMIC` is per open file description in the same way the framebuffers are, and it decides what the two property-list doors answer: a client that has not set it is **not shown** the properties Linux flags `DRM_MODE_PROP_ATOMIC` - the connector's `CRTC_ID`, the CRTC's `ACTIVE`/`MODE_ID`/`OUT_FENCE_PTR`, and the planes' `FB_ID`/`CRTC_ID`, both rectangles and the two fences - while `GETPROPERTY` asked for one **by id** still answers and still reports the flag. That is Linux's rule, measured on the host's card before it was written: six properties on a CRTC for an uncapped client and nine for a capped one, seventeen and eighteen on a connector, and a second descriptor of the same card kept its own answer. Pinned by `t-drm-props`. A `SYNCOBJ_FD_TO_HANDLE` import with `IMPORT_SYNC_FILE` lands its destination on a point, and the two `TIMELINE` flags decide *which*, measured both ways: without the flag it is the **fence's own point**, *set* rather than raised (a destination at 4 imported from a plain object's `sync_file` reads 0 afterwards, and one imported from a timeline's reads that timeline's point, which the exporting object's own `point` snapshots at export - an export *asked for* point 5 from an object at 9 lands 9); with the flag the request names it and it *raises*, like every other point writer here (4 with 2 asked for stays 4, with 6 goes to 6). Either way the destination **becomes a timeline**, point 0 included, so a plain object that refuses `TIMELINE_WAIT` answers it from point 0 after an import. Pinned by `t-drm-sync`. A property write is either **recorded and read back, or refused**: a value the property's own advertised range or enum does not hold is `EINVAL` (`max bpc` 16 was the first of these; `DPMS` 9 and `ACTIVE` 2 followed it, each sharing *one* value list with the read path so the shape a caller reads and the shape a write must match cannot drift), and an accepted write is what the read-back says - `pixel blend mode` records `Coverage` or `Pre-multiplied` rather than steering nothing and answering `Pre-multiplied` to both (nothing here composites: the scanout is the compositor's finished frame, so the value is state, not a mode). A blob-typed property is judged by the *same* test the commit path uses rather than by a second one: `MODE_ID` names a blob holding a mode this card can show, or 0 for none - a commit naming anything else was already `EINVAL`, and the single-property door recording an id that named nothing was the two doors disagreeing about one property. Pinned by `t-drm-props`, which reads the card's own mode back from `GETCONNECTOR` and stores it as the blob it names rather than assuming what a mode is. Other §7.4 gaps closed: `DRM_CLIENT_CAP_CURSOR_PLANE_HOTSPOT` is **accepted** (per open file description, like `ATOMIC`) and the cursor plane publishes `HOTSPOT_X`/`HOTSPOT_Y` behind it - a signed range bounded by the largest cursor this card answers for (`DRM_CAP_CURSOR_WIDTH`/`HEIGHT`, 64) - so a client that has not set the cap is not shown them and one that has reads back what it wrote. Binding or moving the cursor plane hands the pointer to the host over the virtio-gpu **cursor queue** (`UPDATE_CURSOR`/`MOVE_CURSOR`) when the device has one; where it does not, the kernel blends the cursor into the scanout instead. The earlier refusal of this cap was measured against a non-virtualized amdgpu and did not apply to this device (§7.4). Pinned by `t-drm-props` (cap + hotspot gating) and `t-drm` (an `RMFB` of the cursor's framebuffer takes the plane's binding down, leaving no dangling host resource). |

### 2.1 `futex`'s operation word, per command

`futex(2)` is one dispatch arm (`nr::FUTEX` → `proc::handle_futex`) over a *command* word, and
the refusal lives at operation level: an unimplemented command reaches
`note_missing_futex_op`, which prints `mpos: futex op {op:#x} -> ENOSYS` once per number — the
one refusal `note_enosys` cannot describe, because it is keyed by syscall number and every one of
these arrives as `futex`. Served commands, measured in `src/syscall/linux/proc.rs`:

| Command | Value | Verdict | Pin |
|---|---|---|---|
| `FUTEX_WAIT` | 0 | Served (relative deadline; `FUTEX_CLOCK_REALTIME` selects the clock) | `t-futex`, `t-wait-eintr` |
| `FUTEX_WAKE` | 1 | Served | `t-futex` |
| `FUTEX_FD` | 2 | Refused `ENOSYS` (Linux removed it in 2.6.26) | `note_missing_futex_op` names it in the log |
| `FUTEX_REQUEUE` / `CMP_REQUEUE` / `WAKE_OP` | 3, 4, 5 | Refused `ENOSYS` | " |
| `FUTEX_LOCK_PI` / `UNLOCK_PI` / `TRYLOCK` | 6, 7, 8 | Refused `ENOSYS` (no priority-inheritance futexes) | " |
| `FUTEX_WAIT_BITSET` | 9 | Served — an empty bitset is `EINVAL`, which is Linux's answer and the claim `t-futex` opens with | `t-futex` |
| `FUTEX_WAKE_BITSET` | 10 | Served | `t-futex` |
| `FUTEX_CMP_REQUEUE_PI` / `WAIT_REQUEUE_PI` | 12, 13 | Refused `ENOSYS` | " |
| `FUTEX_PRIVATE_FLAG` | +128 | Accepted on any command — this kernel is uniprocessor, so shared and private are one table | `t-futex` |
| `FUTEX_CLOCK_REALTIME` | +256 | Honoured on the wait forms (measured above) | `t-futex` |

The owner is `src/syscall/linux/proc.rs` (`handle_futex`); the wake side is
`crate::sched::futex`. A caller that needs only mutex/condvar traffic never leaves the served
rows; anything asking for priority inheritance or requeueing reads the honest `ENOSYS` with its
operation named in the log.

### 2.2 Request words, by whole encoding

The dispatch filters on the **whole** `_IOC_TYPE` magic (`family_nr`,
`src/syscall/linux/fs/ioctl.rs`) — never on the command byte alone, the rule §12.1 A8's
`RNDADDENTROPY` incident exists to enforce. The families and their magic bytes are the table
above; the individual words a pin asserts against live in the guest programs named there
(`t-ioctl` carries the `'R'` family as a table of whole command words, `t-vt` reads the `'V'`
words out of the shipped headers rather than recalling them, `t-drm-lease` pins the lease family
against `<drm.h>`'s literals).
