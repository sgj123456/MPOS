**Status: 15.1–15.6 landed, all four of 15.6's pins green. 15.1, 15.3, 15.4 and 15.5 and the init
seam unified - all four check families run on both machines, the reporting/exit-hook/net/cmdline/log-sink

`mpos login:` in 16 s, and `depgraph` within the ratchet. `### 15.6` below records what it cost.
The last named difference this machine carried from the first - `init_net` +
`virtio::spawn_service` behind `mpos.selftest` - is also closed, measured the same day.
Measured 2026-10-07.** *(This header is that day's snapshot; the phase has since landed through
§15.36. Two of its words are retired facts, not current ones: `boot-aarch64`/`alpine-aarch64`
are commands §15.7 deleted — the same work is `run`/`rootfs`/`test --arch aarch64` — and the

Phase 13 closed the *ABI* gap (13.3–13.16) and §13.19/§13.20 closed two of its consequences. What
is left is the *boot*: the second machine reaches the same userspace surface as the first, but it
gets there along its own path, and the parts of that path which are not about a bus, a UART or a
page-table format are written twice - once in `src/board/x86_64.rs`, once in `src/board/aarch64.rs`.
The goal of this phase is that the machine-independent half of the boot has **one** copy, so that
"which machine is this?" is answered by the machine layer and by nothing else.

Of the four missing capabilities, three are hardware absence on this port and one is port work:
`mpos_msi` and `mpos_fpu_trap` have no counterpart here (a `virt` machine with a GIC and no `#NM` -
both honest "absent", not stubs), and `mpos_qemu_debug_exit` is an emulator exit port AAVMF does not
answer. `mpos_pci_config` is *not*: the bus is there, but it is not the bus this port drives its
devices over - the device tree is. The three that *have* crossed over are the ones whose device was
already reachable over that tree: `mpos_input_registry` (§13.24), the console (§13.25) and
`mpos_framebuffer_console` (§13.26, on the `virtio-gpu` card the same MMIO transports carry) - each
by handing the same device to the shared driver instead of opening it, reading its identity and
dropping it.

### The target shape

1. **One home for the neutral checks.** `src/board/checks/{mm,sched,vfs,ipc,report}.rs`, under the
   wiring crate for the reasons `board/steps.rs` already records (the depgraph lets the wiring name
   the machine and both libraries; `boot` would close a mutual pair with `vfs`). A body keeps a
   private `devices()` and a private `arch_checks()`; everything else is called from one place.
2. **One `init` seam.** `mpos_arch::arch::boot`'s `init` callback becomes `fn(&BootInfo) -> !` for
   both machines. This is what makes "the same sequence, both machines" expressible at all: the
   aarch64 fork exists only because it stashes the archive before the switch, and *that* is a
   consequence of (3).
3. **One root-switch flow: the second machine gets an initramfs `/init`, like the first.** The
   kernel unpacks the archive and hands the machine to `/init` on both machines; the *script* mounts
   `/proc`, `/sys`, `/dev`, `root=` and pivots. That is Linux's own model, it is what
   `docs/ARCHITECTURE.md` §4 and `AGENTS.md` §4 rule 1 require ("a kernel that assembles them first
   leaves pieces the owner of the system cannot unmount"), and it deletes `check_disk_root`'s mount
   half and `switch_root` outright. The alternative - moving the pivot into the kernel for *both*
   machines - is the same line count with more risk: it re-implements the script's `root=`/
   `rootfstype=`/`rootflags=` loop in Rust, breaks `cargo xtask run`'s "no `root=` → drop to a shell
   in the initramfs" behaviour, and contradicts §4. Cost of the chosen direction: one
   `initramfs-aarch64/` tree plus its toml, a busybox in it (`mount`, `pivot_root`), and `M7_ROOT_OK`
   moving from a kernel marker to a script-printed one - which moves `xtask/src/aarch64.rs`'s
   `TERMINATORS` in the same commit (AGENTS §5's trap: a wrong terminator kills the boot seconds in,
   indistinguishable from a hang).
4. **Nothing machine-independent stays in a body.** After this, `board/<arch>.rs` holds: the entry's
   three callbacks, `devices()`, the machine's own checks (the paging/IDT proof, the UART's TX/RX
   proof, the MMIO transport probes), and the ordering its own milestones need - and every one of
   those is machine work by definition.

### 15.6 The initramfs flow — **LANDED**, all but the Alpine login pin

The stage's whole point was that the second machine stops being the exception: the kernel unpacks
`initramfs-aarch64/`, hands the machine to the script, and the *script* mounts `/dev/vda`, promotes
it into `/` and `switch_root`s into the disk's own `/init` - the flow `AGENTS.md` §4 rule 1 and
`docs/ARCHITECTURE.md` §4 require, and the one the first machine has always run. `check_disk_root`'s
mount half became `steps::mount_disk_root` (called from `init` exactly where x86_64's `init_blk`
calls it, with the wrapper deleted outright), `M7_ROOT_OK` stopped being a kernel marker, and the
`init` seam is one signature (`fn(&BootInfo) -> !`) on both machines.

After this, no line in the boot flow is written twice for a reason that is not a bus, a UART or a
page-table format. What each body holds is the shape §"The target shape" item 4 names: the entry's
callbacks, `devices()`, the machine's own device discovery and checks, and the ordering its own
milestones need.


### What stays the machine's, by design

PCI vs device tree; MSI vs GIC line routing; the lazy-FPU trap (no `#NM` on arm64); the two UARTs;
the page-table/IDT proofs (`check_arch`); the console arming order (`steps::arm_console` is *called*
at different points on purpose). None of these is duplication to remove; the phase's rule is the one
`board/mod.rs` already states - a body holds only what would have to be answered differently on a
different machine.

### Known traps for this phase

- **The aarch64 sweep's payload is not the x86_64 harness's machine.** Measured while writing
  §13.20's pin: the x86_64 test `/init` mounts `/proc`, `/sys`, `/dev`, `/tmp`, `devpts` with
  busybox; the aarch64 runner mounts only `/tmp`. A test that needs `/proc` therefore behaves
  differently per machine, and one that does (this phase's shared checks will) must either mount what
  it needs or be honest about the difference. Closing *that* gap is itself part of stage 15.1's
  argument.
- **The marker chain is no longer asserted by a command of its own** (§15.7). The checks still
  print their `M*_OK`/`M*_FAILED` markers on every boot and a failure still halts the machine, so a
  red boot is readable off the wire - but nothing parses the chain any more: what a boot's verdict
  is, on either machine, is the sweep's `=== RUN/PASS/FAIL/SUMMARY`/`END`.
- **A check that mutates shared state damages the machine it checks** (§13.14, §13.15).
- **A device check runs on every aarch64 boot, a session included**, and halts the machine when it
  fails: `check_blk` needs the 1 MiB pattern image beside the disk, `check_fs` needs the root
  partition to carry `/hello`. Both are therefore inputs of *any* aarch64 image, not only a test's
  (`disk::blk_image`, `Arch::kernel_reads_root_probe`). *(Superseded by §15.34: the checks now
  assert only what the kernel produces from the configured devices — no packed fixture, no
  `/hello`; `PROBE_FILE`/`PROBE_BYTES`/`Arch::kernel_reads_root_probe` are gone. What survives of
  this bullet is the first clause: a device check runs on every boot and halts the machine.)*

### 15.9 The kernel travels inside the loader — **LANDED**

The boot volume carries one bootable file, not a stub beside a kernel. `boot/build.rs` compresses
the kernel this build is for (DEFLATE, `miniz_oxide` level 9) into the loader's own image, and
`boot/src/lib.rs` inflates it from the `include_bytes!` of that payload before it opens the volume.
The ESP's root now holds `EFI/BOOT/BOOT<ARCH>.EFI`, `initramfs.tar` and `mpos.cmdline`, and no
`mpos.elf`. This is Linux's `bzImage` shape, with the parts named: the stub is still a stub, the
kernel is still not a firmware application, and every step of the load path but the first is
unchanged.

**Why a build script and not a path.** The shorter spelling - `include_bytes!` of a fixed path - is
wrong for the one reason this crate has to be careful: the kernel is the input that *moves*. Cargo
rebuilds a crate when something it declared moved, and a path written in the source declares
nothing, so the loader would go on carrying the previous kernel with no word said. `build.rs`
declares the two dependencies that are real - `MPOS_KERNEL_ELF` (which `xtask` always sets, to the
kernel it has just built, so a self-test boot and an ordinary boot each carry their own) and the
file's own bytes (`cargo:rerun-if-changed`). The same crate appears in `[dependencies]` *and*
`[build-dependencies]` on purpose: a compressor from one project and a decompressor from another is
a pair that drifts, and what it drifts into is a boot that dies on a stream it cannot read.

**Why the other two stay files.** They are data the kernel is handed and unpacks itself, not
programs the loader has to place in memory and jump to. Carrying them would mean relinking the
loader into a larger image every time a file in the early userspace changed - and there is a
distribution's worth of them. Linux draws the line in the same place.

**Measured** (the two machines, 2026-10-10):

| | compressed | loaded | loader |
|---|---|---|---|
| x86_64 | 809 KiB | 2396 KiB (33%) | 64 KB -> 912 KB |
| aarch64 | 834 KiB | 2288 KiB (36%) | 66 KB -> 937 KB |

Both serial logs carry the new line - `mpos-boot: kernel image: 809 KiB compressed, 2396 KiB
loaded` on the first, `834 ... 2288` on the second - and `build/<arch>-sweep-esp` holds three
files. The bytes the volume carries *fall* (64 KB loader + 2.4 MB kernel becomes one 912 KB file),
so the compression pays for itself in the one place it was not needed.

**What it deliberately does not do.** `run()` still loads an image and jumps to it: `elf.rs` (379)
and `vm.rs` (256) are untouched and the kernel is still not a PE. This is therefore **not** step 1
of `TEST-AND-BOOT-REFACTOR.md` §5 - which now records it as §5.8 - but takes §5's *visible* half
(one artifact, no `mpos.elf`) without any of its costs. The three costs §5.7 named - one allocator
serving two firmware phases, the `x18` clash that makes `none` and `uefi` unable to be correct at
the same time, and the loss of the `-kernel` bare-metal path - all remain unpaid, because none of
them follows from the kernel being *carried*; they follow from the kernel being *started by the
firmware*.

**One guard got smaller, and the comments now say what it guards.** `HANDOFF_MAGIC`'s reason used
to be "an older `mpos.elf` left on a partition". The kernel is inside the loader now, so the record's
two ends are always built together and cannot disagree by accident; the check stays - it is one
comparison, and a boot volume assembled or half-updated by hand is still a thing to refuse - and
`src/boot/handoff.rs`, `docs/modules/boot.md` and `docs/modules/loader.md` were reworded rather than
left naming a file that no longer exists.

**The first version of this was wrong, and the way it was wrong is worth keeping.** The build
script watches the file `xtask` hands it and decides freshness the way a build script must - from
that file's modification time. The trouble is that cargo links an already-compiled artifact into
place *keeping the artifact's own compile time*, while the two kernels this front end builds (the
ordinary one and the self-test one) land at the **same** path in the target directory. That path is
therefore one whose mtime can stand still while its bytes change - and the case where they change is
exactly the alternation between the two. The first gate after this landed showed what that
produces: the second machine booted, printed every line up to `mpos: /init is up`, and then stopped
for **fourteen minutes** with nothing on the wire. What had booted was the *ordinary* kernel carried
into a self-test boot, and the early userspace was waiting for ever on a console line only a
self-test kernel queues. Three things came out of it.

* **The fix is at the build, not at the boot.** The loader is handed a path its *caller* owns -
  `build_kernel` the target directory's `mpos`, `build_test_kernel` its own copy under `build/` - so
  the two values differ, and switching between them reruns the build script before the file's own
  change is even considered. The copy is *mirrored* rather than copied (the bytes are compared
  first), so an unchanged kernel does not relink the loader and recompress it on every test run.
* **The runtime guard that "should" have made it loud is refused by this repository's own gate, and
  the refusal is right.** Reading a test word off the command line in the boot's own code is
  forbidden (§15.19 - whether a kernel carries tests is the *build's* to say, not a word's and not a
  run-time check's). The attempt was made, a host gate named it by file and line, and the guard was
  removed. It is also why `boot::cmdline_has` has no caller at all: it is the one spelling of a
  question the boot is not allowed to ask.
* **A host test now pins the cheap half**: the two kernels must reach the loader as two *different*
  paths (`xtask/src/utils.rs::the_loader_is_handed_a_path_each_kernel_build_owns`). The property
  itself - an mtime that does not move forward - cannot be unit-tested; naming the invariant can, and
  it turns a fourteen-minute hang into a one-second failure.

The build script also reports *which* file it embedded and by which route (`MPOS_KERNEL_ELF` or
derived from `TARGET`), because "a loader carrying the wrong kernel" is a failure whose symptom
names everything except its cause.

**Gates, after the fix.** aarch64 `165 staged, pass=165 fail=0` (the 165th is `t-virtgpu`); x86_64
`161 staged, pass=161 fail=0`; host unit tests 102; the kernel's 29. In the first version of this
section those numbers were `164`/`161` with host tests `101`; `xtask/src/fat.rs`'s 8.3 example was
`mpos.elf` and is now a name that stands for the class, because nothing the ESP carries fits in
8.3 any more.

### 15.12 The card is handed back when the process ends, not only when it closes — **LANDED**

Moving `t-drm` to the std side (§15.11, batch 45) put five `drm*` programs in **one boot** where
before they had been split across two images, and the first gate that ran them found three of them
red for a reason that was nobody's assertion: `t-drm`'s own three connector-property claims, and
then - the tell - `t-drm-args`' `MODE_ATOMIC ... is EFAULT` answering `EACCES`, and `t-drm-lease`'s
"a non-master cannot create a lease" answering success. That is not a card being wrong; it is a card
that still believes somebody else is its master.

**The mechanism.** `drivers::drm::master_closed` - the function that gives back a description's
master, its console binding, its client-capability set, its authorisations, its sync objects and its
framebuffers - is called from **one** place: the `close(2)` syscall's hook in `file.rs`. A process
that ends without closing its card never runs it, and *every* test ends that way: `Report::finish`
is `std::process::exit`, which is `exit_group`, which unwinds nothing - the `OwnedFd`s on `main`'s
stack are never dropped and `close` is never called. So `t-drm`, which sets `DRM_CLIENT_CAP_ATOMIC`
and takes the master, left both behind. The second half is why it poisoned a *different* program: an
`ofd` is the open file description's address (`file.ofd()` is `Arc::as_ptr`), so once the description
is freed the allocator hands the **same address** to the next one - and `t-drm-props` opens a fresh,
deliberately *uncapped* description and asserts it is not shown the atomic properties. It was.

**The fix is the missing registration, not a test-local cleanup.** `master_closed`'s own header
already promises the property ("a compositor that is killed - or a test that simply closes the card -
must not leave the machine holding a screen nobody can drive"); the implementation just delivered it
on the syscall path and not on the exit path, and `sched::exit` exists for exactly this shape
(`src/sched/exit.rs`: a subsystem registers a hook and the teardown walks the list without knowing
what is on it, so `sched` never names `drivers`). `drivers::drm::close_at_exit` is that hook; it uses
`vfs::file::for_each_last`, the same "is this the final reference" rule the close hook applies by
hand, so a card a `fork` still holds is left alone. It is registered in
`board::steps::register_exit_hooks` beside locks, the socket and the inotify watch - the three that
were already every machine's - in registration order, which is the order the resources have to go.
`t-drm` additionally hands the card back itself (`DROP_MASTER`) before it returns, which is the
explicit form of the same courtesy and the one claim the move added; with the hook in place the two
agree.

**The other two findings are the migration's own and are recorded in the §15.11 row** (batch 45):
two records the no-std original handed the kernel four bytes short of what the kernel's `arg_shape`
copies - `drm_mode_obj_get_properties` (`sizeof` 32, passed 28) and one `ADDFB2` (`sizeof` 104,
passed 100) - and a two-element property array that the kernel's all-or-nothing copy rule
(`want >= count`) had been writing through, which the std side's correctly sized array stopped.

**Gates.** aarch64 `168 staged, pass=168 fail=0`; x86_64 `161 staged, pass=161 fail=0`; host unit
tests 522; the kernel's 29. `t-drm` is 122 claims, per claim identical on both machines, and it is
the second machine's first run of the family.


### 15.13 `ADDFB2` read its modifier four bytes early — **LANDED**

`struct drm_mode_fb_cmd2` is `sizeof` 104, and its `modifier[4]` begins at **72**: `handles[4]` is
20..36, `pitches[4]` 36..52, `offsets[4]` 52..68, and 68..72 is the padding the `__u64` forces.
Measured, not counted — a `cc` probe against the installed uapi headers answers `sizeof` 104 and
`offsetof(drm_mode_fb_cmd2, modifier)` 72 (`.workbuddy/drmpropsize.c`, the same shape as
`.workbuddy/leasesize.c` and `.workbuddy/drmsize.c`).

`add_fb2` read the modifier at 68 and `get_fb2` wrote it back at 68. Both are fixed.

**Why nobody saw it.** The only modifier any caller ever named was `DRM_FORMAT_MOD_LINEAR`, which
is 0. Reading the padding instead of the field answers 0 as well, so `LINEAR` was accepted for the
right reason by the wrong bytes, and `GETFB2` reported a modifier a caller would find at 72 - where
it was zero too. The no-std `t-drm-props` could not have caught it for a worse reason: it spelled
its offsets by hand, in the same wrong place, so the test and the kernel agreed with each other and
with nothing else. That is the pair this migration separates — the std side states the uapi's
number as a compile-time assert, and the kernel was moved to answer it.

**How it is pinned.** `t-drm-props` names a modifier this plane does not list and expects `EINVAL`.
The constant matters as much as the offset: `DRM_FORMAT_MOD_BOGUS` is `0x0100_0000_0000_0000` -
vendor 0x01's namespace with the value 0, a real-shaped `drm_fourcc.h` vendor modifier whose **low
32 bits are zero**. A four-bytes-early read sees the padding plus the value's low half, which is 0,
so it takes a modifier it cannot scan out and calls it `LINEAR`. The original constant ended in
`...0001`, whose low half is nonzero, so the refusal came out the same at either offset and the bug
stayed invisible — the constant had to change, not just the offset.

**Both directions are measured**, on the first machine:

* kernel at 68, test at 72 — `FAIL: ADDFB2 refuses a modifier the plane does not list (got 0, want
  -22)`. The bogus modifier was accepted.
* kernel at 72, test at 72 — `pass=161 fail=0`.

`t-drm` (batch 45) had been green across the whole bug, and still is: its `ADDFB2` carries `LINEAR`
and its `GETFB2` read-back asserts zeros, and both answers are 0 at 68 and at 72. A green test is
not evidence about a field nothing has ever written a nonzero value into.

**Gates.** aarch64 `169 staged, pass=169 fail=0`; x86_64 `161 staged, pass=161 fail=0`; host unit
tests 522; the kernel's 29. `t-drm-props` is 98 claims, per claim identical on both machines, and
it is the second machine's first run of the family.


### R.15 (moved from ROADMAP's status board) — the card at exit, the ADDFB2 offset, and what the 3D work still has not measured

**A process hands the card back when it ends, not only when it closes (§15.12).** The DRM master, its console binding, the client-capability set, the authorisations, the sync objects and the framebuffers were released by the `close(2)` hook alone, and `do_exit` never runs it: `Report::finish` is `std::process::exit`, which is `exit_group`, which unwinds nothing, so a description that ended without closing its card left its DRM state behind. Because an `ofd` is the description's *address*, the next description the allocator placed there inherited a claim it never made. Found when five `drm*` programs first shared one boot — `t-drm` broke `t-drm-args`, `t-drm-lease`, then `t-drm-props` — and fixed by registering `drivers::drm::close_at_exit` with `sched::exit` beside locks, the socket and the inotify watch, so the exit path delivers the property `master_closed`'s header already promised.

**`ADDFB2` reads its format modifier at the offset the uapi gives it (§15.13).** The field is at 72, not 68: `offsets[4]` ends at 68 and 68..72 is the padding the `__u64` forces, measured against the installed headers. `add_fb2` read at 68 and `get_fb2` wrote at 68, and the no-std test it was written against spelled its offsets by hand in the same wrong place, so the two agreed with each other and with nothing else.
